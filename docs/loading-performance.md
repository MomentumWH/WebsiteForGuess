# 项目加载优化记录

## 主要原因

1. 项目根目录的 `.pnpm-store` 包含 323,037 个文件。Vite 默认忽略 `node_modules` 和 `.git`，但不会自动读取 Git 忽略规则排除这个本地依赖缓存。调试暂停时调用栈停在 Chokidar 的 `_addToNodeFs`、`_watchWithNodeFs` 和 Node `fs.watch`，说明大量时间用于注册文件监听。独立开发服务基线测试中，入口脚本等待 8 秒后超时；旧服务的首页请求也无法在 5 秒内完成。
2. 原始根组件全局加载 Naive UI 的主题、消息、对话框等后台服务；公共赛事首页并不使用这些组件。路由初始化同时加载会话、权限状态和 Axios，扩大了公共首页的依赖链。
3. 后台仅用 7 种图标，但从图标库总入口导入，增加开发扫描和构建工作量。
4. 球场 JPG 背景为 720,964 字节，超过优化后全部首页脚本的大小。

## 已实施

- 在 `server.watch.ignored` 中排除 `.pnpm-store` 和 `.idea`，保留业务源码热更新。
- 显式预处理 Vue、Vue Router、Pinia；不在启动时递归扫描全部懒加载后台路由。后台独有依赖仍可按请求发现与预处理。
- 启用 `strictPort`，端口占用时明确报错，避免不知情地切换到另一个端口。
- 根组件只组合路由；后台主题与组件服务放入异步 `AdminProviders`。路由尚未解析时不提前加载后台组件。
- 公共赛事路由直接通过；会话初始化与原有权限逻辑移入异步 `adminGuard`，仅进入后台或登录页时加载。
- 图标改为具体文件导入，提前处理实际使用的 7 个小图标模块，避免首次登录跳转时触发开发服务重新优化、刷新页面。
- 背景转换为 1440 × 960 的 WebP，并在 HTML 中提前请求；原始 JPG 保留作为素材。

## 同机实测

2026-10-12，Windows / Node 24.12.0 / Vite 7.3.7，本机回环网络。

| 指标                                         |          优化前 |                  优化后 |
| -------------------------------------------- | --------------: | ----------------------: |
| 独立开发服务入口脚本响应                     | 8,009 ms 后超时 |                   80 ms |
| 开发服务启动至监听就绪（包含进程与配置加载） |        2,367 ms |                1,869 ms |
| 生产首页实际加载的 JS 原始体积               |       472,492 B | 157,879 B（减少 66.6%） |
| 球场背景                                     |       720,964 B | 287,660 B（减少 60.1%） |
| 构建处理模块数                               |           4,142 |                   2,819 |

脚本体积来自同一浏览器禁用缓存后的 Resource Timing，计入入口、首页及共享辅助脚本，不把后台按需文件算进首页。体积是解码后字节数，不是启用压缩后的网络流量。开发时延是单次采样，受磁盘缓存、系统负载影响；不能直接等同于所有机器上的完整页面加载时间。

## 复测

运行 `pnpm perf:dev` 会在 4451 端口启动隔离的开发服务，依次检查 HTML、入口、Vue 依赖和工作台模块，并在监听初始化后再次请求首页。完成后自动停止测量服务；超时或非 200 响应会返回失败状态。第二次运行同一标签可检查缓存后的启动。

运行 `pnpm perf:dev fresh-label` 可使用一个新的依赖缓存目录进行冷启动检查。端口 4451 应空闲。正常开发继续使用 `pnpm dev`，默认端口 4444；生产预览使用 `pnpm preview`。

新增后台依赖无需禁止自动发现；只有频繁使用、希望提前优化的小型运行时依赖才需要加入 `optimizeDeps.include`。不要将 `.pnpm-store` 重新纳入监听范围。
